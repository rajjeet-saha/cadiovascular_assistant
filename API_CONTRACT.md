# 4. Common Rules

## Content-Type

Requests containing JSON must use:

Content-Type: application/json

## Patient ID

Every patient-related request must use:

patientId

Example:

"P001"

Do NOT use:

patientID
patient_id
userId


## Timestamp

Backend-generated timestamps use ISO 8601 format.

Example:

2026-09-18T18:30:00.000Z


## HTTP Status Codes

200 = Successful request

201 = Successfully created

400 = Invalid request

404 = Resource not found

500 = Server error

# 5. Patient API

## Create Patient

### Request

POST /patients

### Body

{
  "patientId": "P001",
  "name": "Test Patient",
  "hospitalId": "H001",
  "doctorId": "D001",
  "age": 60
}

### Parameters

patientId = unique patient identifier

name = patient name

hospitalId = hospital identifier

doctorId = assigned doctor identifier

age = patient age


### Example Response

{
  "success": true,
  "message": "Patient created successfully",
  "patientId": "P001"
}

# 7. Health Readings API

This is the main API for wristband health data.

## Send Health Reading

### Request

POST /health-readings

### Body

{
  "patientId": "P001",
  "heartRate": 78,
  "spo2": 98,
  "battery": 85,
  "activity": 2,
  "ecg": 512
}


## Parameters

### patientId

Type: String

Example:

"P001"


### heartRate

Type: Number

Unit: BPM

Example:

78


### spo2

Type: Number

Unit: %

Example:

98


IMPORTANT:

Always use:

spo2

Do NOT use:

SpO2
oxygen
oxygenLevel
spo2Level


### battery

Type: Number

Unit: %

Example:

85


### activity

Type: Number or String

Example:

2

The team may use:

0 = Resting
1 = Walking
2 = Running

The exact activity mapping can be changed later,
but the parameter name must remain:

activity


### ecg

Type: Number or Array

Example:

512

For a single ECG sample:

"ecg": 512

For multiple ECG samples:

"ecg": [512, 514, 511, 516]


## Timestamp

The backend automatically creates the timestamp.

The mobile app does not need to send a timestamp
for the basic health-reading request.


## Example Response

{
  "success": true,
  "readingId": "R001",
  "data": {
    "patientId": "P001",
    "heartRate": 78,
    "spo2": 98,
    "battery": 85,
    "activity": 2,
    "ecg": 512,
    "timestamp": "2026-09-18T18:30:00.000Z"
  },
  "alertsCreated": []
}

# 9. Alert System

Alerts are generated by the backend.

The mobile app does NOT independently decide whether a
medical reading is abnormal.

The backend checks the configured patient thresholds.


## Current Prototype Thresholds

Default values:

heartRateMin = 50

heartRateMax = 100

spo2Min = 94


IMPORTANT:

These values are prototype/demo rules only.
They are NOT medical diagnostic thresholds.


---

# 10. Alert Types

The following alert type names are fixed:

ABNORMAL_HEART_RATE_HIGH

ABNORMAL_HEART_RATE_LOW

LOW_SPO2

SOS


Do not rename these values.


---

# 11. Alert Object

Example:

{
  "alertId": "A001",
  "patientId": "P001",
  "type": "LOW_SPO2",
  "parameter": "spo2",
  "value": 90,
  "threshold": 94,
  "status": "active",
  "acknowledged": false,
  "message": "SpO2 below configured threshold",
  "createdAt": "2026-09-18T18:30:00.000Z"
}


## Alert Parameters

alertId = unique alert ID

patientId = patient ID

type = alert type

parameter = parameter that caused the alert

value = measured value

threshold = configured threshold

status = alert state

acknowledged = whether patient acknowledged it

message = human-readable message

createdAt = alert creation time


## Status Values

active

acknowledged

resolved

# 19. Mobile App Responsibilities

Person 3 and Person 4 are responsible for the mobile application.

The mobile app must:

1. Connect to the ESP32 using BLE.

2. Receive:
   - patientId
   - heartRate
   - spo2
   - ecg
   - activity
   - battery
   - sos

3. Display health information.

4. Send health readings to:

POST /health-readings

5. Retrieve patient information using:

GET /patients/{patientId}

6. Retrieve health history using:

GET /health-readings/{patientId}

7. Retrieve alerts using:

GET /alerts/{patientId}

8. Allow the patient to acknowledge alerts.

9. Display medications.

10. Display appointments.

11. Send SOS alerts.

# 29. Error Handling

If patientId is missing:

{
  "success": false,
  "message": "patientId is required"
}


If patient does not exist:

{
  "success": false,
  "message": "Patient not found"
}


If the server encounters an error:

{
  "success": false,
  "message": "Internal server error"
}


The mobile app and doctor dashboard should handle
these errors without crashing.

# 34. Prototype / Safety Notice

This project is a college prototype.

The system is intended for monitoring, demonstration,
data visualization, reminders, and rule-based alerts.

It must not be represented as a medical diagnostic system
or as a medically validated device.

Abnormal readings used during demonstrations should be
synthetic test data.

Threshold values in this document are prototype configuration
values and are not medical advice.
